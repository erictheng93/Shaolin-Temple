# 技術選型與執行限制

記錄日期：2026-11-05，更新 2026-11-06。狀態：前端已建立於 `web/`；後端框架選定 Axum，依 [BACKEND_TASKS.md](BACKEND_TASKS.md) 實作中；玩法第一版為參拜（合十、跪拜、上香、敲鐘，2026-11-15），計分與持久化尚未定義。

## 產品與工程優先順序

開發手機與 PC 瀏覽器可直接進入的多人靜心遊戲，以《山寺》（Sansatemple）類型為參考。優先考量執行時資源消耗、運行效率與穩定性，並將手機發熱、耗電、聲音體驗與首次可操作時間列為主要品質指標。

3,000～5,000 人同時在線是產品容量目標；目前未確認是全站總在線或單一房間彼此可見，相關同步設計先採可分房／分區的工作假設。容量目標尚未經過實測。

## Vue 版本與安裝規範

本專案採用 **Vue 3.5.44**。這是本次確認的穩定版本基準；後續即使上游發布新版本，也不會自動改變本專案的選擇。

建立前端 `package.json` 後，在前端套件目錄執行：

```bash
npm install --save-exact vue@3.5.44
```

預期 `package.json` 的相依套件包含：

```json
{
  "dependencies": {
    "vue": "3.5.44"
  }
}
```

以上是片段，需合併到骨架產生的完整檔案。版本使用精確字串，不加 `^` 或 `~`。若骨架直接宣告 `@vue/compiler-sfc`，將它與 Vue 固定為相同版本。

提交 `package.json` 與 `package-lock.json`；CI 與可重現安裝使用：

```bash
npm ci
```

安裝完成後可用下列指令檢查實際版本：

```bash
npm ls vue
```

Vue 單檔元件使用：

```vue
<script setup lang="ts">
import { ref } from 'vue'

const soundEnabled = ref(false)
</script>

<template>
  <button type="button" @click="soundEnabled = !soundEnabled">
    {{ soundEnabled ? '關閉聲音' : '開啟聲音' }}
  </button>
</template>
```

此範例只展示元件語法與 UI 狀態，實際音訊由 AudioManager 處理。

## 前端邊界

Vue 管理選單、音量設定、房間資訊、個人計數與連線提示。獨立的 TypeScript 遊戲核心管理以下工作：

| 模組責任 | 工作 |
| --- | --- |
| SceneRenderer | Three.js 場景、鏡頭、畫質與渲染排程 |
| AnimationSystem | 角色動作、插值與動畫更新 |
| NetworkClient | WebSocket、訊息編解碼、重連與狀態恢復 |
| AudioManager | 長音軌、短音效、音量與暫停恢復 |

以上模組已實作於 `web/src/game/`，由 `GameCore` 擁有並負責建立與釋放順序。高頻玩家狀態直接供遊戲核心使用，UI 只透過 `UiState` 接收低頻摘要（內容改變時才推送，最多每 250 ms 一次）。

直接使用 Three.js 的目的是控制高頻更新與依賴邊界；它不保證在相同場景下比所有封裝更快。效果須由相同素材、畫質、裝置與互動負載的量測判斷。

### 渲染排程

- 前景時一律以畫質的幀率上限繪製（標準 30 FPS，高畫質 60 FPS），高更新率螢幕會略過多餘的 rAF。庭院有持續的環境動畫（落葉、樹冠、香煙），所以不停止迴圈；沒有手動的省電畫質，省電分成下面兩個自動機制。
- 平常就省電：15 秒沒有操作也沒有移動（`IDLE_AFTER_MS`）時，幀率上限降到 20 FPS（`IDLE_FPS`），一有操作立即恢復。這不必等到掉幀才反應——手機通常先發燙很久才掉幀。
- 動態畫質（`core/AdaptiveQuality.ts`，智慧省電）：網頁讀不到裝置溫度，所以只看實際幀間隔——過熱降頻、人數變多或裝置較慢都會表現為幀變慢。每 2 秒判斷一次：平均幀間隔超過「目標 × 1.35 且超過 28 ms」就降一級；低於該門檻的 85% 並持續 30 秒才升回一級；升回後 30 秒內又撐不住，下次等待時間加倍（上限 240 秒）。超過 1 秒的間隔視為暫停，之後觀望 3 秒。等級 0～3 依序為：解析度倍率 1／0.85／0.7／0.6，完整模型與投影的半徑 14／14／9／5 公尺（`ADAPTIVE_LEVELS`）。手動選的畫質是上限，動態調整在其下運作；效能資訊會顯示目前等級。門檻數值未經手機實測校正。
- 切到背景時停止迴圈、暫停 AudioContext、停止送出位置；回前景時重設時間基準並直接把鏡頭移到定位。
- 繪製像素同時受 devicePixelRatio 上限與總像素上限限制。

### 已知限制與後續

- 角色是 Q 版小沙彌公仔：`web/scripts/build-avatar.mjs`（`npm run build:avatar`）以程式產生整尊模型（不依賴外部模型檔）：光滑的橢球與旋轉體組成頭、耳朵、鐘形的袍、寬袖、合十的手與鞋尖，沒有稜角；輸出 `web/public/models/monk.glb`（約 4,400 面、103 KB）與遠處用的 `monk-lod.glb`（約 1,600 面、41 KB），各含 body 與 skin 兩個節點（袍色來自 instanceColor，袖口與鞋子以頂點色壓暗）。臉不在模型上，由 `AvatarFactory` 把五官畫在圖集、貼合在頭的正面。沒有 UV 與骨架，動畫是整尊傾斜、壓扁與彈跳；之後若用 Blender 展 UV、烘焙法線，輸出同樣兩個節點即可取代。模型載入前或載入失敗時以圓柱與球代替。
- 角色以 InstancedMesh 批次繪製，不論人數都是 7 個 draw call：身體、膚色部分與臉（五官圖集，各取自該 tier 的頭部幾何，不投影）各分近、遠兩批，加上影子。離本機玩家 `nearRadius` 內用完整模型（約 4.4 千面）並投射即時陰影（只有高畫質有陰影貼圖）；之外用低面數模型（`monk-lod.glb`，約 1.6 千面、41 KB）且不投影，只留腳下的假影子。桌面 Chromium、mock 伺服器 15 人、高畫質：等級 0 時 56～58 draw call、約 15.8 萬三角形（含陰影 pass）；等級 3 時約 5.6～8.7 萬三角形、繪製解析度由 1280×720 降到 768×432。手機未實測。名牌為個別 sprite，只顯示最近 12 人。批次容量 160（`AVATAR_CAPACITY`），需大於最高畫質的可見人數。
- 可見人數上限（標準 60／高畫質 120）仍需依手機實測調整；人數多時主要成本轉為三角形數與透明的影子重疊。
- 移動碰撞只把角色推出障礙物，不做尋路。
- 音效為合成音色，正式錄音可透過 `AudioManager.loadSfx()` 替換。
- 環境音（風聲、鳥叫、遠鐘）見下方「環境音」。
- 協定為 JSON 草案，欄位以 Rust 後端定案為準。
- 尚未做手機實機的發熱、耗電與 20～30 分鐘幀時間測試。
- 上方「已量測」表格的庭院數字是改為寫實材質之前量的，draw call 與三角形數以「庭院視覺」一節為準（含靜態光照烘焙後的數字）；FPS 尚未重新量測。

### 庭院視覺（寫實材質）

方向：小範圍場景、寫實材質與光照；幾何仍是程序化產生，寫實模型（樹、建築細部、角色）待 Blender 減面流程建立後替換。

- **材質**：`MeshStandardMaterial`＋ Poly Haven 的 CC0 貼圖（鋪石、石牆、紅灰泥、屋瓦、草地、樹皮），原檔放在 `web/assets/textures/<id>_<diff|nor|rough>_<512|1k>.jpg`，以 `npm run build:textures`（需 Khronos KTX-Software 的 `ktx`，PATH 或環境變數 `KTX`）編碼成 `web/public/textures/` 的同名 `.ktx2`（ETC1S/BasisLZ，含 mipmap）。執行時由 `KTX2Loader` 依裝置轉成 ASTC／ETC2（手機）或 BC（桌面），GPU 記憶體約為未壓縮的 1/4～1/8，也省掉主執行緒解 JPEG 與產生 mipmap；轉碼器是 three 附的 `basis_transcoder`，複製在 `web/public/basis/`，升級 three 時要重新複製（`basis.test.ts` 會檢查）。UV 以公尺為單位（`texBox`、`hipRoof`），紋理密度不隨物件大小改變。貼圖載入前顯示底色，載入後才套用；相同網址只上傳一次。
- **光照**：程序化天空（three 的 `Sky`，大氣散射）烘成 PMREM 環境貼圖提供環境光與反射，不需要 HDR 檔；低角度暖色主光；ACES 色調映射只用於戶外，殿內維持原本未經色調映射的畫面。WebGL context 恢復時重新烘環境貼圖。
- **陰影**：靜態物件的陰影與環境光遮蔽事先在 Blender 烘焙（見下方「靜態光照烘焙」），執行時靜態物件不進陰影貼圖。即時陰影貼圖只留給角色：標準畫質（手機預設）完全不建陰影貼圖，角色只有腳下的假影子；高畫質保留 2048 的陰影貼圖，只有近處角色投影，地面與靜態物件接收。
- **屋頂與圍牆**：`hipRoof()` 產生下緩上陡、四角起翹的曲面屋頂（主殿重簷、鐘亭攢尖）；庭院外圍有石基紅牆瓦頂的圍牆與山門缺口，距可走範圍約 3 公尺，不需要碰撞。
- **未採用後製**：試過 GTAO 環境光遮蔽與泛光，透明的香煙 sprite 在遮蔽 pass 產生黑塊、天空泛光讓畫面發白，已移除。

| 畫質 | 即時陰影貼圖 | 貼圖 | 細節貼圖 | 烘焙貼圖 | 貼圖下載量 |
| --- | --- | --- | --- | --- | --- |
| 標準（手機預設） | 無（角色只有假影子） | 512 | 底色＋法線 | 512（圖集＋地面） | KTX2 約 0.88 MB（JPG 為 0.61 MB）＋烘焙 116 KB＋轉碼器 gzip 約 0.26 MB |

#### 靜態光照烘焙（2026-11-15）

- **內容**：每張烘焙貼圖是線性的 LDR 遮罩（不是 HDR lightmap）：RGB = 環境光遮蔽（三通道相同），A = 太陽可見度（靜態物件互相投下的影子）。ETC1S 的 RGB 與 A 是兩個獨立壓縮的 slice，影子硬邊不會干擾 AO（若放在 R／G，同一個 4×4 區塊內各通道只能一起變化）。AO 走 three 內建的 `aoMap`（只壓暗半球光與天空環境光、反射）；太陽可見度由 `courtyardBake.ts` 的 `patchBakedSun`（`onBeforeCompile`）乘在平行光的直接光上，法線貼圖與太陽高光照常計算。沒有 `aoMap` 時沒有 `USE_AOMAP`，等同未修改；只裝在庭院接收烘焙的材質，殿內不受影響。
- **兩張貼圖**：地面（草地、鋪石、步道）以世界座標 xz 平面投影到 x、z ∈ [-30, 30]（範圍外取邊緣值，所以範圍要涵蓋圍牆影子）；其餘靜態物件排進圖集。Blender 裡地面類物件以一塊 y = 0.06 的平面代表（高於鋪石與步道頂面），共用同一層結果。
- **第二組 UV（uv1）在執行時產生**：`render/lightmapUv.ts` 依幾何的 groups 切 chart（方塊每面、圓柱側面與上下蓋、屋頂每坡；`hipRoof` 為此加了 group），chart 內沿用原本以公尺為單位的貼圖 UV，以實際尺寸換算成一致的密度（朝下的面 1/4），再以 shelf packing 排進 1024 的圖集（chart 四周 6 texel，Blender 以 margin 延伸填滿）。執行時與烘焙匯出走同一份程式，不下載 UV 資料。靜態的共用幾何（柱、樹幹、香、竹竿）因此由 InstancedMesh 改為一般 Mesh 再依材質合併（每個需要自己的烘焙區域；draw call 不增加）。`mergeStatic` 保留 uv1。
- **一致性**：匯出時算出幾何指紋（接收者的世界座標與 uv1、擋光物件的靜止姿態、太陽方向與烘焙設定，量化後雜湊），烘焙完成後寫進 `courtyardBake.generated.ts`。`courtyardBake.test.ts` 在 CI 比對目前程式算出的指紋，不符就失敗：改了庭院幾何、太陽方向或烘焙設定就要重新烘焙。執行時只在開發模式（`import.meta.env.DEV`）重算並比對，不符時退回即時陰影並在 console 警告；正式版不計算指紋（`fingerprint()` 為延遲計算，正式建置中沒有呼叫端），直接載入烘焙貼圖。理由：正式版若因 JS 引擎浮點差異誤判而退回，標準畫質（沒有陰影貼圖）的手機會整個庭院沒有影子。
- **快取**：`public/` 下的檔案 Vite 不加雜湊，烘焙貼圖網址帶 `?v=<指紋>`，重新烘焙後網址改變，瀏覽器與 CDN 不會拿舊貼圖配新幾何。
- **動態物件**：樹冠（隨風輕晃）、晾衣以靜止姿態當擋光物件烘進地面，本身不接收烘焙；鐘以靜止姿態烘焙並接收，擺動時烘焙值跟著鐘走（擺幅小）；燈籠只有自發光閃爍，照常烘焙；落葉、香煙、遠山不參與。
- **退回**：烘焙貼圖載入前、載入失敗或（開發模式）指紋不符時，靜態物件照舊投射即時陰影（高畫質看得到；標準畫質沒有陰影貼圖，畫面沒有影子但其餘正常）。兩張都套上後才關閉靜態物件的投影。WebGL context 恢復後由 three 重新上傳（已以 `WEBGL_lose_context` 驗證）。
- **載入成本**（正式建置、桌面 Chromium（headless，V8）、5 次，非手機）：產生 uv1（`prepareLightmapUvs`）中位數 12.6 ms（12.2～15.3）；依材質合併（`mergeStatic`，烘焙前就有，現在多帶 uv1）3.8 ms（3.6～6.6）；整理烘焙資料 0.1 ms（0～0.2）；指紋計算（只在開發模式執行）4.1 ms（3.6～5.7）。烘焙貼圖的轉碼在 worker，未計入。手機尚未量測，預期數倍於此。
- **流程**：`npm run bake:lightmaps`（`scripts/bake-lightmaps.mjs`）以 Vite 在 Node 執行 `buildPlainCourtyard()`、匯出到 `web/.bake/`（不提交）→ `blender -b --factory-startup -P scripts/bake-lightmaps.py`（Blender 5.3、Cycles CPU，桌面約 30 秒；Blender 由 PATH 或環境變數 `BLENDER` 指定）→ 寫入指紋 → `build-textures.mjs lightmaps` 編碼成 `public/lightmaps/courtyard_{atlas,ground}_{512,1k}.ktx2`（PNG 原檔在 `assets/lightmaps/`，第一列是 uv1 的 v = 0）。也可 `--export-only` 後在已開啟的 Blender（例如經 MCP）設定 `BAKE_ARGS` 執行同一支 Python，再 `--finish`。不產生 .blend 檔。
- **烘焙設定**（`BAKE_SETTINGS`）：太陽方向取自 `OUTDOOR_SUN_POSITION`（與 `SceneRenderer` 的戶外主光共用）、視直徑 1°；AO 距離 2.5 公尺、128 samples；太陽可見度＝兩次只含直接光的 DIFFUSE 相除（有影子 ÷ 全部不投影），32 samples。Cycles 的 SHADOW 烘焙在全影處不是 0，新 world 預設的 0.05 灰色環境光也會算進直接光，兩者都已排除。
- **解析度**：圖集 texel 約 8.6 公分（1k）／17 公分（512）；地面約 5.9 公分（1k）／11.7 公分（512）。檔案大小：圖集 1k 192 KB、512 70 KB；地面 1k 158 KB、512 46 KB。
- **已知限制**：uv1 在執行時產生，圖集排版依浮點比較（chart 大小以 ceil 取整、依高度排序）。不同 JS 引擎（例如 iOS 的 JavaScriptCore）的 Math.sin／cos／pow 末位若不同，極少數情況可能讓某個 chart 的大小或排序改變，使圖集排版與烘焙時不同、該處影子錯位；正式版不檢查指紋，不會發現。尚未在 iOS 實機驗證（桌面 Chromium 算出的指紋與 Node 相同）。若發生，可改為把 uv1 排版結果（chart 位置）隨貼圖一起發佈。角色走進烘焙的影子裡不會變暗（標準畫質角色只有腳下假影子；高畫質角色仍投影到地面）。太陽方向固定，不能做時間變化。標準畫質的 512 貼圖在牆面、屋頂上的影子邊緣較模糊；預算內（約 300 KB）可改用 1k 的地面貼圖（標準畫質合計約 227 KB），尚未採用。

| --- | --- | --- |
| 烘焙前（全部靜態物件進陰影貼圖） | 46～47 draw、約 3.5 萬三角形 | 46～47 draw、約 3.5 萬三角形 |
| 烘焙後 | 26～27 draw、約 1.8 萬三角形 | 28～29 draw、約 2.2 萬三角形 |

### 殿內場景（少林寺）

- 兩個場景（zone）：`courtyard`（庭院）與 `hall`（殿內），定義在 `src/game/world/zones.ts`：各自的可走範圍、障礙物、出生點、出入口、鏡頭距離與室內鏡頭邊界。場景建模、碰撞與（未來的）伺服器驗證都以此為準。
- 進出：庭院走到殿門階梯前（或點擊主殿建築，會自動走向殿門）即淡出黑幕進殿；殿內走回門口回庭院。出入口落點刻意放在對面出入口範圍外，避免來回瞬移（有測試）。殿內場景第一次進殿時才建立（桌面約 28 ms）。

- 神像方位依傳統以神明為主體：中央釋迦牟尼佛；主佛左手邊（龍邊，參拜者看去的右邊、+x）觀世音菩薩；右手邊（虎邊，參拜者看去的左邊、-x）關聖帝君。

### 環境音

沒有背景音樂，聲音留白大於填滿：只有風聲、鳥鳴與偶爾的遠處鐘聲，全部在執行時合成，不下載任何音檔、不需要 R2 音訊素材或環境變數。

- 風聲：6 秒單聲道雜訊 AudioBuffer（單極點 lowpass 白噪音，尾段 1 秒以等功率交叉淡化疊回開頭，可無縫循環），接 lowpass（450 Hz、Q 0.7），增益 0.05 ± 0.03、截止頻率 450 ± 200 Hz，分別由 0.11 Hz 與 0.07 Hz 的 LFO 緩慢調變，形成陣風起伏。走環境音軌，由「環境與音樂」音量控制。
- 鳥叫：每 4～14 秒一次的短 AudioBuffer（偶爾有另一隻回應）；遠處頌缽每 25～55 秒一次。
- 遠處鐘聲：每隔 90～210 秒隨機一聲，沿用寺鐘音色，播放速率 0.85、lowpass 500 Hz、增益 0.1，餘韻長。只在本機播放，不經網路，不觸發庭院鐘亭的擺動，也不喚醒渲染迴圈。常數在 `AudioManager.ts` 開頭。
- 靜音或總音量為 0：淡出後暫停 AudioContext；「環境與音樂」為 0：風聲、鳥叫、頌缽與遠鐘停止，音效仍可播放；背景：同靜音。環境音停止時計時器全部清除，恢復後重新排下一次，不會累積補響。
- 風聲與遠鐘的音量依設計值設定，尚未在手機上實聽調校。

## 載入、渲染與音訊方向

- 首次只載入基本場景、自己的角色與必要互動；其他玩家及非必要素材分批加入。
- 將下載、模型解碼、物件建立、貼圖上傳與 shader 編譯分開量測。
- 手機先以穩定 30 FPS 為調校起點，限制繪製總像素，提供可調整畫質；實際門檻待裝置測試後決定。
- 使用烘焙光照、共用材質與幾何，限制動態陰影、後製與完整骨架動畫數量；遠景可採簡化模型或 sprite。
- 畫面靜止時停止或降低重繪；持續動畫仍需對應的繪製頻率。聲音播放與 3D 重繪分開管理。
- 背景時暫停繪製，依產品需求降低網路活動；恢復前景後校正動畫時間與房間狀態，處理 WebGL context loss。
- 長誦經與環境音優先評估 HTMLMediaElement；短音效使用 Web Audio buffer。使用者操作後啟用播放，提供獨立音量與淡入淡出。
- 共用素材採明確的資源擁有權；離開場景時釋放不再使用的 GPU、音訊及連線資源。

以上為初始工程方向，尚非經過驗證的效能保證。

## 物理引擎

**決定（2026-11-15）**：需要物理時採用 Rapier；目前不引入任何物理引擎，也不改用 Godot、Bevy 等遊戲引擎。

現況：角色是平地上的運動學角色，碰撞由 `world/zones.ts` 的 2D 障礙物＋尋路處理，伺服器以移動額度與直線檢查驗證，沒有重力或剛體的需求。敲鐘、上香、木魚、坐禪等互動都是動畫片段，不是物理。

**何時需要、怎麼做**

| 互動類型 | 例子 | 做法 |
| --- | --- | --- |
| 預先設計的動作 | 敲鐘、上香、合十 | `GameplayModule` 加動畫片段，不用物理 |
| 地形有高低 | 台階、斜坡 | 先用高度資料＋射線；不夠再用 Rapier 的 `KinematicCharacterController` |
| 本機裝飾性物理 | 投錢幣、落葉、搖籤筒 | 各自在本機模擬、不同步，只同步結果（例如「投中了」） |
| 多人共享物理 | 一起踢毽子、推石球 | 伺服器以 `rapier3d` 權威模擬，前端用同一引擎預測；成本最高，非必要不做 |

**為什麼選 Rapier**

- 前後端同一套引擎：後端是 Rust，可直接用 `rapier3d`；前端用同一引擎的 WASM 版本，碰撞行為一致，碰撞形狀可只定義一份（目前障礙物已在 `layout.ts` 與 `server/src/world.rs` 各抄一份，不宜再多一份行為不同的引擎）。
- 持續維護、效能好、靜止物體自動休眠。
- 不選 cannon-es：純 JS、2022 年後幾乎沒有更新、較慢，後端無法共用。
- 不改用 Godot／Bevy：網頁版首次下載數十 MB（Godot 4 引擎約 30～40 MB、Bevy WASM 約 10～30 MB），手機首次開啟慢，且要重寫已可運作的前端；物理可以單獨補上，不需要換掉整個引擎。若日後改做原生 App 且玩法轉為重度即時動作，再重新評估。

**引入時的限制**

- WASM 約 1.5～2 MB：以 `import()` 延遲載入，只有安裝了需要物理的玩法模組才下載，不進首次載入。
- 固定步長，每秒 30 次模擬，與渲染頻率分開；背景分頁時停止。
- Rapier 的 world 由該玩法模組擁有，`install()` 回傳的清除函式中釋放（`world.free()`）。
- 新增依賴時依「Vue 版本與安裝規範」以精確版本寫入並記錄於上表。

## 後端：Axum

2026-11-06 選定 Axum 0.8（當時最新 0.8.9），不採用 Actix-web。理由：

- 直接建立在 tokio 與 hyper 上，房間 actor（tokio task + channel）與 WebSocket 使用同一個執行環境，沒有額外的 actor 系統要學。
- WebSocket 為官方功能（`ws` feature），可設定單則訊息上限。
- 中介層使用 tower 生態（逾時、CORS、追蹤），與 `tower-http` 共用。
- 本專案的負載以長連線廣播為主，兩者的 HTTP 吞吐差異不是瓶頸；選擇以維護成本與生態一致性為準。

已確認參數：單一房間上限 50 人（`ROOM_CAPACITY`），超過時開新房間。任務拆分、驗收標準與稽核流程見 [BACKEND_TASKS.md](BACKEND_TASKS.md)。

### 流量基準（前端量測）

協定新增批次位置 `moves`（每個 tick 一則，只含有變動的玩家，座標精度 0.01 公尺）。以 mock 伺服器 50 人滿房、約半數機器人持續走動並隨機做動作，量測單一客戶端 20 秒：

| 項目 | 結果 |
| --- | --- |
| 接收量 | 約 6.1 KB/s |
| 訊息數 | 約 12.3 則/s（`moves` 約 9 則/s、`action` 約 3 則/s） |

預算為每人每秒 150～460 bytes，此情境超出 13～40 倍。機器人移動頻率高於靜心遊戲的預期行為，屬偏悲觀的估計；後端仍須以「靜止不送、降低 tick、二進位量化」為設計前提，並在 T7 以實際負載量測。

## 多人同步方向

瀏覽器使用原生 WebSocket 封裝，渲染選型與連線協定保持獨立。Rust 伺服器確認座位、房間加入結果及操作合法性。

- 分房或分區訂閱，控制每位玩家接收的其他玩家數量。
- 移動時按需要更新位置；停止移動後停止持續重送相同座標。
- 禮佛等動作傳送動作類型與開始時間，由各客戶端播放動畫。
- 初次加入傳送快照，之後傳送差異；重連時取得可恢復的一致狀態。
- 設定訊息大小、操作頻率與每連線佇列上限；尚未送出的過期位置可合併。
- 需要確認的操作與可取代狀態分開處理，避免重試產生重複副作用。
- JSON 或二進位編碼、位置量化、更新頻率依實測決定；先控制廣播範圍，再優化封包。

PostgreSQL 儲存持久資料，避免每個位置或動畫更新都寫入資料庫。資料庫連線池大小依主機與查詢負載調校，不依在線玩家數逐一建立連線。

## VPS 與部署限制

| 項目 | 使用者提供規格 |
| --- | --- |
| 節點 | Linode Tokyo |
| CPU | 1 vCPU；Shared／Dedicated 類型未提供 |
| RAM | 2 GiB |
| 儲存 | 50 GB SSD |
| 每月流量額度 | 2 TB |
| 出站頻寬 | 最高 2 Gbps |
| 入站頻寬 | 未提供 |

保留 Dokploy 作為選定部署工具。這台主機同時執行作業系統、Dokploy、代理、遊戲服務與 PostgreSQL 時餘裕有限；文件不宣稱已能承載 3,000～5,000 名活躍玩家。正式承載量須以整套部署環境壓測判定。

建置放在 CI，主機接收成品。設定日誌輪替、舊映像清理、資料庫備份與服務資源監控。單台主機故障或維護會影響所有連線，部署與重連流程必須納入驗收；單機配置不提供高可用性。

R2 使用自訂網域與快取提供素材，設定必要的 CORS 與版本化快取策略；WebSocket 狀態仍由 VPS 傳出。入站埠速與出站額度是不同條件，2 Gbps 也不代表整月可以持續以該速率傳送。

### 流量預算範例

假設 2 TB 為十進位、每月 30 天，並把全部額度分配給遊戲出站資料：

| 在線情境 | 每玩家平均可用出站資料 |
| --- | --- |
| 3,000 人整月持續在線 | 約 257 bytes/s |
| 5,000 人整月持續在線 | 約 154 bytes/s |
| 每天 8 小時有 5,000 人，其餘時間零流量 | 約 463 bytes/s |

公式：`每玩家 bytes/s = 2,000,000,000,000 / 每月總玩家在線秒數`。上述數字尚未扣協定、心跳、重連與其他請求，實際需預留餘額。

另一個假設：`5,000 接收者 × 30 名被觀察玩家 × 5 次/s × 32 bytes = 24 MB/s = 192 Mbps`。若此負載持續，約 23 小時就會使用 2 TB，尚未計協定開銷。這是流量算例，不是系統壓測結果。

## Phase 2：Tauri Mobile

沿用前端遊戲核心，以 Tauri 封裝 Android／iOS 應用程式。Tauri 使用平台 WebView，Three.js 仍在 WebView 執行；封裝不保證降低 GPU 負載、發熱或耗電。

進入 Phase 2 前，需先驗證 WebView 的圖形相容性、背景／前景恢復、音訊中斷、素材快取與弱網路重連。核心素材可評估隨應用程式分發，活動素材仍由 R2 提供。

## 容量與品質驗證

壓測需區分總連線、活躍玩家、同時移動／操作比例與每人訂閱人數。負載產生器放在外部機器，正式部署上的 PostgreSQL、Dokploy 與代理一併納入測試。

至少記錄 CPU、RSS、可用記憶體、訊息佇列長度、出站流量、斷線率、伺服器處理時間與客戶端操作延遲；包含持續運行、弱網路、慢速接收者及大量重連情境。

手機實測包含首次可操作時間與連續遊玩至少 20～30 分鐘後的幀時間、耗電與發熱；以固定裝置、亮度、音量及網路條件比較。通過標準在第一次實測後依產品需求制定。尚未執行上述驗證。
