# 負載測試報告（T7）2026-11-12

目的：量出「每位玩家每秒的出站流量」與伺服器資源用量，並和 [TECH_STACK.md](TECH_STACK.md) 的流量預算比較。**這是開發機本機迴路的量測，不是目標主機（1 vCPU／2 GiB）的容量聲明**，數字不能直接外推到正式環境（見「限制」）。

## 量測環境

| 項目 | 內容 |
| --- | --- |
| 機器 | Intel Core i7-13700F（16 核心／24 執行緒）、15.9 GB RAM、Windows 11 IoT Enterprise LTSC 2024 |
| 伺服器 | `server/target/release/temple-server.exe`（`cargo build --release`，rustc 1.95.0），`PORT=18080`、`RUST_LOG=warn`，其餘為預設（`ROOM_CAPACITY=50`、`TICK_HZ=10`） |
| 負載工具 | `server/target/release/loadtest.exe`，獨立程序，與伺服器在同一台機器，經 127.0.0.1 連線 |
| 每個情境 | 重新啟動一個伺服器程序；負載工具以 5 ms 間隔建立連線，等 2 秒暖機後量測 60 秒 |
| 指令 | `loadtest --url ws://127.0.0.1:18080/ws --connections N --moving-ratio R --seconds 60 --ramp-ms 5 --settle-ms 2000` |

### 模擬玩家的行為（對照前端 `NetworkClient.ts`）

- 送 `hello` 後等 `welcome`，取出生位置。
- 「移動中」玩家以 10 Hz 送 `move`：庭院邊界內（向內縮 1 m）隨機走動、速度 2.5 m/s（伺服器容許 3.2 × 1.5 m/s）、座標取到 0.01，碰到邊界轉向。移動比例 10%／50% 是「整個測試期間持續移動的玩家比例」，且均勻分散在各房間。其餘玩家不送位置。
- 全部玩家：每 10～25 秒一次 `action`（`bow`／`bowl`／`bell`，遠低於每秒 2 則的上限）、每 20 秒一次 `ping`（前端 `heartbeatMs`）。
- **房間上限 50 人**：50 連線 = 1 個房間；200 連線 = 4 個房間；500 連線 = 10 個房間（各房間均為 50 人，伺服器 `/metrics` 的 `temple_rooms` 與 `temple_rooms_by_players` 已確認）。每位玩家只看得到同房的人，所以每連線接收量只取決於「房內移動中的人數」，與總連線數無關；總連線數只影響伺服器的總負載。
- 每連線流量只計 WebSocket 文字訊息的 JSON 長度（不含 WebSocket 框架、TCP／IP 標頭）。

### 伺服器 CPU／RSS 的取樣方法

PowerShell 腳本（`Get-Process`）每 250 ms 取一次伺服器程序的 `TotalProcessorTime` 與 `WorkingSet64`，取樣區間限定在負載工具印出「量測開始」到「量測結束」之間（約 60 秒）。CPU % = 區間內 CPU 時間差 ÷ 實際經過時間 × 100，**100% 代表用滿一個核心**（24 執行緒機器上可超過 100%）；RSS 為該區間內 WorkingSet64 的平均與最大值。`TotalProcessorTime` 的解析度約 15.6 ms，60 秒區間的誤差約 ±0.03 個百分點，但同一情境重跑的變動遠大於此（見「觀察」）。負載工具本身的 CPU% 以同法取樣，供判斷負載工具是否成為瓶頸。

補充：

- 「出站總頻寬」= 全部連線接收量的總和（負載工具量到的 JSON bytes）；伺服器 `/metrics` 的 `temple_bytes_out_total` 加總與此一致（含暖機期間的 welcome／join）。
- 「tick 間隔」是客戶端量到相鄰兩則 `moves` 的到達間隔（目標 100 ms）。p50／p99 幾乎固定在 94.6／111 ms，是 Windows 預設計時器 15.6 ms 的顆粒度造成（6 × 15.6 = 93.8 ms、7 × 15.6 = 109.4 ms，平均仍是 100 ms），不是伺服器處理變慢；伺服器 tick 處理時間見下。最大值除 500 連線 10% 出現一次 188 ms 外，皆在 112～114 ms。
- 伺服器 tick 處理時間（`temple_tick_seconds`，單一房間一個 tick）：500／50% 平均約 80 µs、最大 1.37 ms；500／10% 平均約 72 µs、最大 1.44 ms；50 連線平均約 63～80 µs、最大 < 0.5 ms。全部情境 `temple_dropped_total`（moves、sync）為 0、`temple_slow_receiver_closed_total` 為 0、`temple_rate_limited_total` 為 0。
- 負載工具 CPU 為 0.8～23.5%（一核=100），最高的情境（500／50%）比伺服器還多；負載工具不是瓶頸，但它與伺服器共用同一台機器的 CPU 快取與排程。

## 與流量預算比較

預算：每人每秒 150～460 bytes（TECH_STACK「流量預算範例」，2 TB 月流量、3,000～5,000 人整月在線，或每天 8 小時 5,000 人）。前端參考值：mock 伺服器 50 人、約半數移動，每位玩家 6.1 KB/s、12.3 則/s。

| 情境（房內移動比例） | 每連線接收 | 相對預算 150／460 bytes/s | 相對前端參考 6.1 KB/s |
| --- | --- | --- | --- |
| 10%（每房約 5 人移動） | 約 1.5 KB/s | 超出 3.3～10.2 倍 | 約 25% |
| 50%（每房約 25 人移動） | 約 5.8 KB/s | 超出 12.6～38.8 倍 | 約 95%（5.8 vs 6.1 KB/s；12.8 vs 12.3 則/s） |

**結論：目前的 JSON 協定在這兩個移動比例下都不符合流量預算**，連 10% 也超出 3 倍以上。50% 的結果與前端用 mock 伺服器量到的參考值一致（差 5%），代表真後端與 mock 的流量量級相同。

主要成本（依本次量到的數字）：

1. **`moves` 位置廣播佔 95～96% 的出站 bytes。** 50%：5,535 的 5,815 bytes/s；10%：1,253 的 1,532 bytes/s。每個 tick 只要房內有人在動，就對房內每位玩家送一則 `moves`（每連線穩定 10 則/s），內容是「其他移動中玩家」的 `[n,x,z,heading,moving]`。每筆 JSON 約 22～26 bytes（5,535 ÷ 10 Hz ÷ 約 24.5 位其他移動者 ≈ 22.6 bytes）。成本約等於「同房移動中的人數 × 10 Hz × 約 23 bytes」，每位移動者對每位觀看者每秒約 230 bytes，單一移動者就已經逼近預算上限。
2. **每則 `moves` 還有固定包裝**（`{"t":"moves","m":[...]}` 約 12 bytes）；10% 情境（每則約 125 bytes）占比較明顯。
3. **其餘 ≈ 280 bytes/s（50%）／≈ 280 bytes/s（10%）來自 `action` 廣播、`ack`、`pong`**：500／50% 共 82,467 則 `action`（共 8.4 MB，約 102 bytes／則）；`welcome`（500 則共約 1.9 MB）與 `join`（12,250 則共約 2.0 MB）只在進房時發生。
4. 玩家人數本身（50 → 500 連線）不改變每連線流量，因為分房後每人只接收同房資料；它只放大總頻寬（0.60 → 23.3 Mbps）。

調整方向（本任務不實作）：T8 的二進位量化把每筆縮到約 7 bytes，約可降為 1/3；但 50% 情境仍約 1.9 KB/s，仍超出預算。要進入 150～460 bytes/s 需要同時減少「同時移動者」的更新頻率與可見人數（降頻、只送視野內玩家、移動比例遠低於本測試的假設）。「靜心遊戲」實際的移動比例需先由真實玩家資料決定。

## 觀察與限制

- **CPU 數字雜訊大**：同一情境重跑差異明顯。500／50% 在本報告最終一輪為 19.3%，先前兩輪為 10.2% 與 8.0%；500／10% 為 9.6% 與 10.7%；200 連線 5.5～6.4%。同機器還有其他程序，**CPU 請視為「約 10～20% 的一個核心」的量級，不要當精確值**。tick 處理（`temple_tick_seconds`）只占約 0.8% 一核（500／50% 每房 10 Hz × 10 房 × 約 80 µs），其餘消耗在連線 task 的 JSON 序列化與 socket 寫入（以排除法推論，未做 profile）。
- **RSS 很小**：500 連線 ≈ 21 MB，每連線增量約 25 KB，量測時間內無持續成長（平均與最大值只差 0.1～0.5 MB）。但每情境只有 60 秒，**不足以證明長時間不洩漏**。
- **tick 抖動**：見上，p99 111 ms 是 Windows 計時器顆粒度；沒有觀察到伺服器端的 tick 延遲（最大處理時間 1.4 ms）。
- **本機迴路**：沒有網路延遲、封包遺失或慢速接收者，所以「丟棄 0、慢速關閉 0」只代表本機迴路下佇列不會滿，**不代表弱網路表現**（慢速接收者與背壓由 `src/room/tests.rs` 的單元測試驗證，不在本報告範圍）。
- **主機差異**：目標是 1 vCPU／2 GiB 的 Linux VPS；本機是 24 執行緒的桌面 CPU。伺服器在 1 vCPU 上的 CPU 占比不能由本表直接換算；也沒有計入反向代理（TLS、WebSocket 轉送）、Dokploy 與 PostgreSQL 的資源。這些留給 T9 在正式環境重跑。
- **出站頻寬只計 JSON 內容**：實際線路上還有 WebSocket 框架（伺服器到客戶端每則約 2～4 bytes）與 TCP／IP 標頭（每則 40 bytes 以上），小訊息時線路流量會比表中高；用 2 TB 月流量規劃時須另外預留。
- **玩法假設**：模擬玩家持續移動、10 Hz 送位置，是偏悲觀的情境；真實玩家靜止時只送一次 `stop`。
- **量測過程的更正**：第一輪量測發現多出 1 個外部連線（名稱 `bobo`，不是負載工具）連到 `localhost:8080`，使房間數與人數多 1；最終一輪改用 `PORT=18080` 避開。同時修正了一個指標問題：`temple_slow_receiver_closed_total` 原本把「對方連線已結束」也算成慢速接收者（第一輪 500／50% 曾顯示 5，實際沒有慢速連線），現在只在發送佇列塞滿時計入。其餘結果的程式與最終一輪相同。

## 重現

```powershell
cd server
cargo build --release
$env:PORT = "18080"; $env:RUST_LOG = "warn"
Start-Process target/release/temple-server.exe       # 另一個視窗／程序
target/release/loadtest.exe --url ws://127.0.0.1:18080/ws --connections 500 --moving-ratio 0.5 --seconds 60
curl http://127.0.0.1:18080/metrics                       # 設了 METRICS_TOKEN 時加 -H "Authorization: Bearer <token>"
```
